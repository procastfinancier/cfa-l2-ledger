How this ledger works — session rules (read this first, every new chat)
Current session focus → Reading 7: Intercorporate Investments (FSA modules 7.1–7.9)
  1. One reading per chat. Each chat session focuses on a single CFA reading. This chat's focus is Reading 7. If the user starts a new chat for a different reading, that chat's own rules panel (or the user) will state the new focus — don't assume it carries over.
  2. Cross-reading questions are fine, but must tie back. Claude can pull in other readings/subjects when quizzing, but every question should connect — even loosely — to the current reading's focus (e.g. linking Reading 7's equity method to Reading 8's pension accounting, or to Equity's residual income model).
  3. Structure everything — glance first, depth on demand. Every explanation the user gives becomes structured HTML, never a paragraph dump. Each point in CONTENT[key].notes carries a module (which section of the reading it sits in, named in MODULES), a gist — one line, always visible, enough to recall the point cold — and a, the full explanation, which renders behind a "Deep dive" dropdown. Writing a point with no gist is a bug: reading only the module headings and gists must still give a complete working picture of the reading. Comparison tables (compares, each also tagged with its module) render inside their own section.
  4. Grill, don't just record. After the user explains a concept, Claude should push for depth on every sub-point of that reading before marking it understood — follow-up questions, edge cases, "what if" variants — not accept a surface-level answer.
  5. Built for real revision. This file is the user's actual November exam revision tool. Bias toward exam-relevant distinctions (IFRS vs. US GAAP, exceptions to ownership-% guidelines, ratio effects) over generic summaries.
  6. Read-only ledger — Claude edits everything. There is no manual-entry UI in this file except the search bar. Explanations happen in chat, not in a textarea; Claude decides status (not started/progress/mastered), writes the structured notes, logs gaps and tuition misses, and sets links between topics — all directly in the file's data. The user never fills in a form here.
  7. Two distinct flag colors — never mix them:
    Amber "Gap" — Claude flagged this during teach-back in this ledger (the user's explanation here was incomplete/wrong) Rose "Tuition miss" — the user got this wrong on an external tuition test/quiz and pasted it in for Claude to log and explain
  8. Tuition-miss workflow. When the user pastes a question they got wrong in tuition, Claude explains the correct answer in chat, then adds it to that topic's TUITION_MISSES entry in the file so it renders as a rose card in the detail view — a permanent, visually distinct weak-spot marker separate from the amber teach-back gaps.
  9. Search bar covers everything. The only interactive control in this file is the search box. It filters on topic names/descriptions AND on the structured content, gaps, tuition misses, status, and links — not just topic titles.
